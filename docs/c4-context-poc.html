Doris SA PoC 架構

依 issue #1，並比照 ADMC 的結構，分成三層：Console 層全公司一個，平台管理者在這裡設定 Doris host、每個 workspace 的 doris path 與 table 權限；Cluster 層每個 fab 一套、components 相同，DLH-Cluster API、Cluster DB、Doris 與 fab Redis 都在這一層；Client 層是 workspace 使用者與各 fab 的 DAO（邏輯分層，DAO 實際部署在各自的 fab）。權限經過兩段同步才會落到 Doris，兩段都用 outbox：Console ⇄ Cluster 把完整權限資料送進 Cluster DB，Cluster ⇄ Doris 再依 Cluster DB 套用到 Doris 並重建 Redis。

System Context

Console 層；粗線是權限同步段 DLH-Cluster 與它的 DB、Redis Doris DAO / Client 人員 fab 部署邊界

權限同步的兩段

段方向內容ADMC 可沿用的模式
1 Console → Cluster
Cluster → Console		 權限變更與 doris_sync_outbox 事件在同一個 transaction 寫進 Console DB。relay 依 cluster_name 把該 fab 的完整權限資料連同 desired_version 送到該 fab 的 Cluster API；Console 的 periodic job 再查回各 fab 的 applied_version 與錯誤。觸發方式有三種，都只是寫一筆 outbox 事件：權限變更時自動、periodic job、trigger API。 Feign ClusterApiClient（每個 fab 一個 endpoint、Basic api-key）；relay 比照 AsyncRequestTask 的輪詢；Console 既有的 scheduler
2 Cluster → Doris、Redis
Doris → Cluster		 Cluster API 只接受比目前新的版本，在同一個 transaction 覆寫 Cluster DB 並寫入 doris_apply_outbox 事件。relay 讀 SHOW GRANTS 和期望狀態比對，只補差異（只動 Console 建立的 SA），再從 Cluster DB 重建本 fab 的 Redis，最後記錄 applied_version。Cluster 也定期重跑一次，修正 Doris 上被手動改掉的權限。 JDBC（MySQL protocol）；Cluster 既有的 Redisson client

待定：Cluster DB 怎麼保存 SA 密碼。Cluster 建 Redis 與下 CREATE USER／ALTER USER 都需要明文，而 issue 規定不能沿用 DLH-Cluster 那把 key。

PoC 範圍

要驗證（依優先順序）

  • Console 上設定的權限，經同步段 1、2 正確落到 Doris
  • 三種觸發都會同步：權限變更時自動、periodic job、trigger API
  • 任一段失敗後，outbox 重試讓 Console DB、Cluster DB 與 Doris 最終一致
  • 白名單：workspace 在該 fab 沒有 doris path 時，寫入回 403；還有授權時不能清空 doris path
  • Console 依 cluster_name 呼叫對的 fab Cluster API
  • 每次套用都從 Cluster DB 重建 Redis；DAO 從 Redis 取得 FE 位址與憑證連 Doris，RBAC 生效
  • DROP USER／REVOKE 後，已建立的連線會不會被踢掉

不在 PoC

  • ADMC 既有 Console / Cluster 程式的修改（PoC 用獨立的精簡版）
  • User action log（沿用 ADMC 既有機制）
  • K8s Secret 與 Vault（以 env var 模擬）
  • 真實的跨 fab 網路
  • Redis 的 eviction、persistence、ACL（Infra 負責）
  • 金鑰輪替流程（只保留 key_version 欄位）
