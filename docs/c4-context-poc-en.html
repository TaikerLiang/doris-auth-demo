Doris SA PoC Architecture

Based on issue #1 and following the structure of ADMC, the system has three layers. The Console layer is one instance for the whole company, where the platform admin registers Doris hosts, each workspace's doris path, and table grants. The Cluster layer is one per fab with identical components: the DLH-Cluster API, Cluster DB, Doris, and the fab Redis. The Client layer holds workspace users and the DAO of each fab (a logical layer; each DAO is deployed in its own fab). Permissions reach Doris through two sync segments, both using an outbox: Console ⇄ Cluster sends the full grant state into the Cluster DB, then Cluster ⇄ Doris applies the Cluster DB state to Doris and rebuilds Redis.

The Two Permission Sync Segments

SegmentDirectionContentReusable ADMC pattern
1 Console → Cluster
Cluster → Console		 A grant change and its doris_sync_outbox event are written to the Console DB in the same transaction. The relay uses cluster_name to send that fab's full grant state, with its desired_version, to the fab's Cluster API. Console's periodic job then reads back each fab's applied_version and errors. Sync has three triggers, each of which just writes an outbox event: automatically on grant changes, the periodic job, and the trigger API. Feign ClusterApiClient (one endpoint per fab, Basic api-key); relay polls like AsyncRequestTask; Console's existing scheduler
2 Cluster → Doris, Redis
Doris → Cluster		 The Cluster API accepts only versions newer than the current one, and in the same transaction overwrites the Cluster DB and writes a doris_apply_outbox event. The relay compares SHOW GRANTS with the desired state and applies only the differences (touching only SAs created by Console), rebuilds the fab's Redis from the Cluster DB, and records applied_version. Cluster also reruns this periodically to revert grants changed by hand in Doris. JDBC (MySQL protocol); Cluster's existing Redisson client

Open: how the Cluster DB stores SA passwords. Cluster needs the plaintext to build Redis and to run CREATE USER / ALTER USER, and the issue rules out reusing the DLH-Cluster key.

PoC Scope

To verify (in priority order)

  • Permissions configured in Console reach Doris correctly through sync segments 1 and 2
  • All three triggers start a sync: grant changes, the periodic job, and the trigger API
  • After a failure in either segment, outbox retries make the Console DB, Cluster DB, and Doris eventually consistent
  • Whitelist: writes for a workspace with no doris path in that fab return 403; a doris path cannot be cleared while grants remain
  • Console calls the right fab's Cluster API based on cluster_name
  • Every apply rebuilds Redis from the Cluster DB; the DAO gets the FE address and credentials from Redis, connects to Doris, and RBAC takes effect
  • Whether existing connections are terminated after DROP USER / REVOKE

Out of PoC scope

  • Changes to the existing ADMC Console / Cluster code (the PoC uses standalone, minimal versions)
  • User action log (reuses the existing ADMC mechanism)
  • K8s Secrets and Vault (simulated with env vars)
  • Real cross-fab networking
  • Redis eviction, persistence, and ACLs (owned by Infra)
  • Key rotation flow (only the key_version column is kept)
