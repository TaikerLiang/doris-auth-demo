C4 Model · Level 1 · System Context

Doris 權限架構

本圖只收錄 Auth、Doris、Client（DAO）三個團隊已達成共識的部分。Doris 只做內建帳密驗證和 RBAC；每個人對應一個 Doris 帳號，由 Tool Console 建立並授權，DAO 再以使用者本人的身分連線查詢。

System Context

關係

#來源 → 目標內容技術
1Data User → Corporate IdP登入，取得 OIDC tokenOIDC
2Data User → DAO Service透過業務系統請求資料，請求帶 tokenHTTPS + JWT
3DAO Service → Corporate IdP驗證 token 簽章後取出 user_id 與 section id；不信任 client 自帶的參數JWKS
4DAO Service → Credential Store以 user_id 讀取該使用者的 Doris 密碼Redis GET
5DAO Service → Doris Platform以使用者本人的 Doris 帳號連線查詢；DAO 不做權限判斷MySQL protocol / JDBC
6Data Owner → Tool Console透過既有 approval workflow 決定哪些資料開給哪些 section 或人HTTPS
7Tool Console → Doris Platformoutbox relay 依核准結果建立帳號、角色、GRANT / REVOKE、row policyJDBC · ADMIN_PRIV 帳號
8Tool Console → Credential Store寫入密碼副本；正本加密存在 Tool Console DBRedis SET / DEL

跨團隊假設

Auth 的設計會產生「每個使用者一個 Doris 帳號」。DAO 必須以使用者本人的身分連線，連線數與同時活躍的使用者數成正比。

  • Doris team：評估 qe_max_connection（預設每台 FE 1024 條）與 FE 數量。
  • Client team：設計依使用者分開的連線池與閒置逾時。

範圍外與已知風險

範圍外

  • 人員離職、調動的偵測與處理：Tool Console 目前無法得知。
  • 效能與容量規劃：由 Doris team 負責。

已知風險

  • 離職者的 Doris 帳號、Redis 密碼與權限會殘留；目前只靠 IdP 停用後 DAO 驗不過 token 來擋。
  • DAO 能以任何人的身分連線，必須被完全信任。
  • Tool Console 的 ADMIN_PRIV 帳號可讀寫所有資料。
